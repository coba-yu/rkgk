# 論文検索 RAG の MVP 設計

更新日: 2026-09-10
状態: アーキテクチャ相談で合意した方針に、設計レビュー（2026-09-10）での決定を反映済み。ライブラリ・モデル・保存形式・前処理との受け渡し形式まで選定完了。未決事項なし。

## 目的

興味のあるカンファレンスやジャーナルの論文を S3 に蓄積し、日本語でテーマを入力すると、次に読む英語論文を快適に探せるようにする。

MVP の主目的は RAG と Knowledge Graph の技術理解である。20〜50本の規模では「日本語要約を全件エージェントに読ませる」ほうが検索として速く正確になりうるが、それに検索品質で勝つことは MVP の要件にしない。Knowledge Graph の役割は候補の増加（recall）よりも、「この論文は手法 X を使い、X は Y の一種である」と根拠付きで説明できること（explainability）を主とする。

実装量を最小限に抑えながら、チャンク検索だけでなく、グラフ経由で候補論文を増やし到達経路を説明するところまで MVP に含める。リッチな UI は作らず、Codex と Claude Code の Agent Skill を入口にする。

## 全体構成

```text
別プロジェクト: 前処理
  PDF → OCR・図・数式の理解 → ページ対応付き Markdown
    └ 論文 ID（連番）を採番し、原本 PDF と処理済み成果物を S3 にアップロード

RAG プロジェクト: 抽出コマンド（論文単位・冪等）
  指定論文の Markdown
    → Python がプロンプトを組み立て、claude -p を JSON Schema 付きで呼ぶ
    → 日本語要約・概念・論文内の関係 JSON を検証し、不備があれば issues を戻して再試行
    → 保存

RAG プロジェクト: 正規化コマンド（全論文横断）
  全論文の抽出結果
    → Python がプロンプトを組み立て、claude -p を呼ぶ
    → 概念の表記ゆれ統合（alias テーブル）と一般知識による概念間関係を検証・保存

RAG プロジェクト: 構築コマンド（Python のみ）
  抽出結果 + 正規化結果
    → チャンク化・ローカル埋め込み・グラフ構築
    → インデックス一式をディレクトリに保存

RAG プロジェクト: 検索 Skill
  日本語のテーマ
    → エージェントが英語クエリを生成（必須）
    → ローカルのチャンク検索（ja / en 複数クエリの和集合）
    → グラフによる候補追加（到達経路付き）
    → エージェントが読むべき理由を生成
    → S3 リンク・日本語要約・読むべき理由・到達経路
```

実行環境は Mac mini M4、メモリ 16 GB。MVP は1台の Mac で利用する。初期検証の規模は20〜50本とするが、将来の総数と追加ペースは未定。

## プロジェクトと実行単位

### 前処理プロジェクト

RAG 本体とは別プロジェクトとする。図・数式の意味理解と OCR は内容を反映するための必須要件であり、MVP から除外しない。RAG 側はプレーンテキストだけの Markdown を正規入力とせず、前処理の成果物が揃ってから結合する。fallback の PDF 抽出は RAG プロジェクトに同梱しない。

サブスクリプション内でのコーディングエージェント利用や、Codex から Chrome を操作して Gemini Web UI を利用する方法が候補として挙がっている。ただし、実行方法・利用条件・品質は未検証であり、今回の設計対象外とする。

論文 ID は連番とし、前処理側が S3 に置く時点で採番する。採番台帳は S3 の `papers/index.json` とし、前処理プロジェクトが更新する。RAG 側は受け取るだけとする。受け渡し形式は「前処理との受け渡し形式」節に定める。RAG 側の単体テストは、この形式で手書きしたフィクスチャで行う。

### 前処理との受け渡し形式

S3 とローカルは同じ構造とする。連番は4桁ゼロ埋めのディレクトリ名で表し、JSON 内の `id` は整数とする。

```text
papers/index.json                  ← 採番台帳。全論文の id / title の一覧。前処理側が更新
papers/0001/paper.pdf              ← 原本
papers/0001/paper.json             ← メタデータ
papers/0001/pages/001.md …         ← 1ページ1ファイル。ファイル名がページ番号
```

paper.json の項目: `id`, `title`, `authors[]`, `year`, `venue`, `page_count`, `doi?`, `arxiv_id?`, `preprocess{tool, version, processed_at}`。S3 URI は含めず、設定の base URI と id から組み立てる。

ページ Markdown は本文をそのまま書き、図と数式は次のマーカーで示す。RAG 側はマーカーを無視しても本文としてチャンク化できる。画像ファイルは RAG 側で受け取らない。

```markdown
<!-- figure: 3 -->
Figure 3 の内容を説明する段落。

$$ y = f(x) $$
<!-- equation: 2 -->
数式 (2) の意味を説明する段落。
```

### RAG プロジェクト

抽出・正規化・構築・検索は、1つの Python プロジェクト内でモジュールとコマンドを分ける。Python コマンドはエージェントが呼ぶ内部インターフェースとし、入出力は JSON とする。

LLM を必要とする処理（抽出、正規化）は、Python が `claude -p --output-format json --json-schema` を subprocess で呼んで行う（PR04 レビューで決定。設計レビュー時の「採用しない」を覆した）。プロンプトは domain の純粋関数として Python が唯一の定義元を持ち、出力はモデルから生成した JSON Schema で固定する。検証に失敗した場合は issues を戻して上限回数まで再試行する。実行先は Claude のみとし、Codex には対応しない。サブスクリプションの範囲内で使えるが、バッチ実行時のレート制限は未検証。

- 抽出コマンドは論文単体で完結し、既存の概念一覧を参照しない。処理順に依存せず、同じ入力から同じ形式の結果を得られる。
- 正規化コマンドは全論文横断の1ステップで、抽出結果を変更しない。表記ゆれや一般知識関係をやり直す際は、論文ごとの抽出を繰り返さない。
- 構築コマンドは LLM を使わず Python だけで完結し、何度でも再実行できる。
- 再抽出・再正規化はコマンドの再実行で済み、手動セッションを要しない。

`claude -p` の prompt cache は Claude Code 自身のシステムプロンプト（約 3,000〜4,000 トークン）にしか効かない（2026-09-11 に実測）。`-p` に渡す本文は完全に同一でも呼び出しごとに cache_creation となり読み出しは 0 で、`--append-system-prompt` に固定文を寄せるとシステムプロンプト分の読み出しまで 0 になる。したがってルールと語彙も本文に含める今の構成を維持し、入力量の削減はプロンプト長でしか行わない。

`codex exec`（0.154.0、ChatGPT アカウント、2026-09-11 に実測）は Codex 自身の指示部分（約 12,900 トークン）が常にキャッシュから読まれ、本文が完全に同一なら 2 回目以降はほぼ全量（約 20,900 / 21,000）が読まれる。ただし先頭 5,000 トークンを共有して末尾だけ違う本文では共有部分は読まれず、指示部分の約 12,900 に戻る。論文ごとに本文が変わる抽出・正規化では Claude と同様にルール部分の再利用は見込めず、この点でも Claude のみ対応の判断は変えない。

抽出 JSON、正規化結果などの中間成果物を保存し、確認・修正と途中からの再実行を可能にする。手で直す場合は成果物の JSON を直接編集する。構築コマンドは読み込み時に構造検証に加えて本文照合も行い、壊れた手編集を検出する（PR04 レビューで決定。validate / save / schema のサブコマンドは持たない）。

検索は既存インデックスだけを使用する。検索中の自動再抽出・再構築は行わず、未構築の論文が分かる場合は案内する。検索時の英語クエリ生成と読むべき理由の生成も `claude -p` で行うかは PR13 で決める。

### レイヤー構成（DDD）

パッケージは DDD の層で分ける（PR03 レビューで決定）。依存の向きは `cli → usecase → domain ← infrastructure` とし、domain は他の層を import しない。

| 層 | 置くもの | I/O |
| --- | --- | --- |
| `rkgk/domain` | エンティティ、語彙、純粋なロジック（マーカー解析、チャンク化、根拠解決、グラフ構築、探索戦略）、外部に求める操作の Protocol | なし |
| `rkgk/usecase` | 処理の入口となるクラス。Protocol 経由で infrastructure を呼び、domain のロジックをつなぐ | なし（委譲のみ） |
| `rkgk/infrastructure` | Protocol の実装。ファイル読み書き、埋め込みモデル、トークナイザ | あり |
| `rkgk/cli/` | ユーザーから呼ぶ単位ごとに 1 モジュール（`extract.py`、以降 `normalize.py` など）で、それぞれを同名のコンソールスクリプトとして登録する（PR04 レビューで決定）。引数解釈と usecase の組み立て、JSON の出力。各成果物の JSON Schema はそのコマンドの `schema` サブコマンドで出す | 標準入出力 |

domain は `models/`、`services/`、`prompts/`、`repositories/` のサブパッケージと `agents.py` に分ける（PR04 / PR05 レビューで決定）。`models/` はデータと不変条件（model validator、Issue / Run、データを持つ例外、モデル由来の `build_*_schema`）だけを概念ごとのモジュールで持つ。`services/` は models を読むだけの純粋なロジック（本文照合、抽出結果との突き合わせ、pydantic エラーの path 変換、今後のチャンク化・根拠解決・グラフ構築・探索戦略）。`prompts/` はエージェントへの指示文を組み立てる純粋関数で、ルールの唯一の定義元として services の検証と並べて保守する。`repositories/` は 1 リポジトリ 1 モジュールで Protocol と例外を持ち、共通基底は `base.py` の `RepositoryError`。`agents.py` は LLM 呼び出しの Protocol。埋め込みモデルなど永続化以外の Protocol は `agents.py` と同列の domain 直下のモジュール（例: `embedders.py`）に置く。依存の向きは models ← services / prompts ← usecase で、models は他を import しない。

usecase は1操作1クラスで `execute()` を持つ。抽出・正規化の検証と保存、構築、検索がそれぞれ usecase になる。infrastructure のテストはフィクスチャで、usecase のテストは fake 実装で行う。

### Skill の扱い

抽出・正規化は Python コマンドが完結させるため、Skill は持たない（PR04 レビューで決定。PR04 で一度作った抽出 Skill は削除した）。検索の入口を Skill にするかは PR13 / PR14 で決める。

## 保存と同期

- S3: 原本 PDF、前処理成果物、抽出結果、正規化結果、構築済みインデックスの永続保存先。
- ローカル: 構築・検索の実行場所と、必要なデータの作業用コピー。
- DB とベクトルストアは導入しない。成果物はディレクトリ1つのファイル一式（JSONL、npy、manifest.json）とし、グラフは networkx でメモリに読み込む。ベクトル検索は numpy のコサイン類似で行う。
- Python は S3 に触らない。S3 との同期は Makefile などから `aws s3 sync` を明示的に実行する。boto3 は導入しない。自動同期と複数端末の同時更新は MVP の対象外。
- 検索用の専用サーバーや AWS の検索サービス・グラフ DB は導入しない。
- 検索時に原本 PDF のローカル保持は要求しない。必要になったらユーザーがエージェントにダウンロードを依頼する。

S3 リンクは設定の base URI と論文 ID から組み立てる S3 URI とする。公開アクセスを前提としない。

## モデルの利用方針

埋め込みは Qwen3-Embedding-0.6B を sentence-transformers（PyTorch MPS）で実行する。日本語のテーマから英語論文を探せることを必須とし、crosslingual の弱さは検索側のクエリ展開と埋め込み対象の追加で補う（後述）。

概念・関係の抽出、正規化、構築時の日本語要約は Python が `claude -p` を呼んで行う。検索時の英語クエリ生成と読むべき理由の生成方法は PR13 で決める。

RAG の Python プログラムから Bedrock などの生成 API を直接呼ぶ構成は採用しない。`claude -p` はサブスクリプションの範囲で使うことを意図するが、利用可能量やレート制限は別途確認が必要。会話中の API 費用試算は仮定単価による参考値であり、採用構成の見積もりではない。

## Knowledge Graph とドメインモデル

### ノード

論文と概念をノードとする。概念の型は `problem`（課題）、`method`（要素技術）、`keyword`（どちらにも分類しない用語）の3つとする。`keyword` は説明・表示のために保持し、グラフ探索の起点・経由地としては既定で使わない（検索設定で有効化可能）。

概念ノードは論文から抽出されたものに限定する。一般知識だけで新しい概念ノードを追加しない。

概念は英語の代表名と、日本語名・略語などの別名を持つ。別名の統合は正規化ステップで alias テーブルとして管理する。同じ意味と判断できるものを統合し、曖昧なものは別ノードとして残す。

### 論文と概念の関係

| 関係 | 意味 | 探索での扱い |
| --- | --- | --- |
| `proposes` | 論文が概念を提案する | 使う |
| `uses` | 論文が概念を使用している | 使う |
| `addresses` | 論文が課題に取り組む | 使う |
| `mentions` | 本文で言及するのみ | 使わない |

「本文に言及がある」と「その論文で使用している」は `mentions` と `uses` で区別する。論文から抽出した関係には、根拠の文章とページ・チャンクへの参照を保持する。

### 概念間の関係

| 関係 | 意味 |
| --- | --- |
| `is_a` | A は B の一種 |
| `part_of` | A は B の構成要素 |
| `used_for` | A は課題・用途 B に使われる |
| `related_to` | 関連するが、上記では表せない |

`related_to` は探索を広げすぎないよう補助的に使う。

概念間の関係は出典区分を持つ。

- `paper`: 論文本文から抽出。根拠の文章とページ・チャンク参照を持つ。抽出 Skill で生成する。
- `general_knowledge`: LLM の一般知識による補完。正規化ステップで、統合後の概念一覧全体を見て一括で提案する。論文ごとには生成しない。

`general_knowledge` の関係も探索に使うが、結果には未検証の補完であることを到達経路に引き継ぎ、原文根拠の関係と混同しない。

### 定義の管理

関係の定義は YAML ではなく Python ネイティブのドメインモデルで管理する。関係名・意味・方向・出典区分・検索での扱いを唯一の定義元にし、抽出用の説明と JSON の検証に利用する。OWL などの形式的なオントロジー言語の導入は決定していない。

## 検索と候補追加

### 埋め込み対象

- 英語本文のチャンク（ページ参照付き）
- 構築時に生成した日本語要約
- 概念の代表名・別名・説明

### 手順

1. エージェントが日本語のテーマから英語クエリを生成する。これは任意ではなく必須の手順で、検索 Skill が指示する。
2. 検索コマンドは日本語テーマと英語クエリの複数クエリを受け取り、それぞれチャンク検索して結果を和集合にする。
3. ヒットしたチャンク・要約・概念に対応する論文を直接の候補とする。
4. その論文の概念（`proposes` / `uses` / `addresses` で結ばれた `problem` / `method`）を起点に、同じ概念を共有する論文を追加する。
5. 概念間の関係を1本たどった先の概念に結びつく論文も追加する。
6. チャンク検索の候補を先に、グラフ経由の追加候補を後に提示する。

### ノイズ対策

- 概念を含む論文の割合が閾値（初期値 40%）を超える汎用概念は、探索の起点・経由地にしない。閾値は検索設定で変更できる。
- グラフ経由の候補は到達経路数の降順に並べる。異なる性質のスコアを合算する順位付けは行わない。
- 同じ論文は重複表示せず、根拠と到達経路をすべて保持する。

### 変更しやすくする箇所

- 関係の種類と意味・出典区分: `domain/vocabulary.py` で管理する。
- グラフ探索: `domain` の戦略 Protocol として検索 usecase から分離し、差し替え可能にする。
- 探索の深さ・対象関係・対象ノード型・汎用概念の閾値・追加候補数: `domain` の検索設定として管理する。
- 順位付け: 探索戦略とは独立して差し替え可能にする。
- 保存形式と埋め込みモデル: `infrastructure` の実装を差し替える。domain と usecase は変更しない。

最初は合意した戦略だけを実装し、将来の戦略を先回りして実装しない。探索結果は到達経路を含む共通形式にして、戦略の変更が Skill や回答生成へ波及するのを抑える。

## 検索結果と回答生成

ユーザー向けの検索結果は、S3 の論文リンク、日本語の論文要約、今回のテーマに対する読むべき理由、グラフ経由の場合はその到達経路の説明を中心にする。

日本語要約は抽出時に生成・保存する。検索時は保存済み要約を利用し、エージェントがテーマに合わせた読むべき理由を追加する。

検索コマンドの出力 JSON には、根拠のチャンク・ページ、グラフ上の到達経路、関係の出典区分、使用した設定を含める。原文の根拠と一般知識の補完を混同せずに説明できるようにする。出力 JSON のファイルへの保存や、読後のフィードバック記録は MVP では行わない。結果の具体的な JSON スキーマは未定。

## 再構築と互換性

ドメインモデルや関係の定義を変更した際は、影響する段階だけをやり直す。

- 抽出 JSON の形式が変わる場合: 全論文を抽出 Skill で再抽出する（手動セッション）。
- 正規化のみ影響する場合: 正規化 Skill だけをやり直す。
- 埋め込みモデルやチャンク設定の変更: 構築コマンドだけを再実行する。

旧形式への後方互換や自動移行は実装しない。成果物ディレクトリの manifest.json に形式のバージョン、埋め込みモデル名と次元、ドメインモデルのバージョン、チャンク設定を記録する。非対応の形式を読み込む場合は明確なエラーとし、暗黙に旧形式を解釈しない。

## 評価の扱い

現時点では正解が分からないため、評価方法や正解セットを定めない。固定の評価テーマや期待論文の整備を MVP の前提にしない。検索結果の保存やフィードバックの記録も MVP に含めない。

埋め込みの検索品質、関係抽出の正確性、一般知識による補完の有用性は、現時点で未検証である。グラフ経由の候補が有用かノイズかを後から判定する手段は MVP には無く、必要になった時点で検討する。

## データモデルと配置

### 実装

ドメインモデルは pydantic v2 で定義する。関係の種類・意味・方向・出典区分・探索での扱いは同じモジュールの Enum とメタ情報で持ち、抽出 Skill 向けの JSON Schema と説明文はモデルから生成して SKILL.md に埋め込む。

Python 環境は uv + Python 3.13、src layout、pyproject.toml 管理。コマンドはユーザーから呼ぶ単位ごとにコンソールスクリプトとして登録し、`uv run extract 1` のように実行する（PR04 レビューで決定）。テストは pytest、lint は ruff。

### エンティティ

```text
Paper            id(連番), title, year?, venue?, s3_pdf_uri, s3_markdown_uri, summary_ja
Chunk            id="{paper_id}:{seq}", paper_id, page_start, page_end, text
Concept          id(slug), canonical_name(en), type(problem|method|keyword), aliases[], description
PaperConcept     paper_id, concept_id, relation(proposes|uses|addresses|mentions), evidence[]
ConceptRelation  source_id, target_id, relation(is_a|part_of|used_for|related_to),
                 origin(paper|general_knowledge), paper_id?, evidence[]
Evidence         page, quote, chunk_id?
```

- 抽出 JSON の概念 ID は論文ローカル（c1, c2 …）。グローバルな概念 ID は正規化 Skill が代表名から slug を割り当て、以後は不変とする。代表名を変えても ID は据え置き、alias で吸収する。
- 抽出 JSON の evidence はページ番号と本文からの引用文だけを持つ。構築コマンドが引用文を本文から検索して chunk_id を付与し、見つからない引用は検証エラーにしてエージェントに修正させる。チャンク設定を変えても再抽出は不要。

### チャンク化

ページファイルを番号順に連結したうえで、見出し・段落境界で分割し、上限（初期値 512 トークン）まで連結する。段落の由来ページから page_start / page_end を付与する。ページをまたぐ段落の連結は行わず、ページ境界はチャンク境界とする。オーバーラップは持たない。

### ディレクトリ

```text
data/
  papers/index.json                     ← 前処理から受領（採番台帳）
  papers/0001/paper.json, pages/*.md    ← 前処理から受領
  papers/0001/extraction.json           ← 抽出 Skill の出力（論文ローカルな概念 ID）
  normalization/concepts.json           ← 正規化コマンドの出力（slug、alias、統合履歴）
  normalization/concept_relations.json  ← general_knowledge の概念間関係
  index/manifest.json, chunks.jsonl, embeddings.npy, graph.json
```

## 次に具体化すること

1. pydantic ドメインモデルの実装と、抽出 / 正規化 JSON のスキーマ生成。
2. 抽出 / 正規化 / 検索の各 Skill の SKILL.md と、対応する Python コマンドの入出力。
3. manifest.json の項目と、検索結果 JSON のスキーマ。
4. 合意形式のフィクスチャ論文で処理が一巡する実装。評価基準はここでは先に固定しない。
5. 前処理プロジェクト側で、この受け渡し形式に沿った成果物を用意する。

## 設計レビューの決定記録（2026-09-10）

| 論点 | 決定 |
| --- | --- |
| MVP の主目的 | 学習目的。検索品質で「全件読み」に勝つことは要件外 |
| KG の役割 | explainability 主 |
| Python から headless CLI 起動 | 採用しない → PR04 レビューで採用に変更（Claude のみ、Skill は削除） |
| 論文 ID | 連番。前処理側が採番 |
| 埋め込み | Qwen3-Embedding-0.6B + sentence-transformers (MPS) |
| 前処理未完でのプレーンテキスト先行 | 認めない。fallback 抽出も同梱しない |
| 概念正規化 | 抽出と分離した全論文横断ステップ |
| 一般知識の概念間関係 | 正規化ステップで一括生成。探索に使い、未検証フラグを引き継ぐ |
| グラフ候補のノイズ対策 | 汎用概念の除外（文書頻度上限）と到達経路数による並び順 |
| 保存形式 | ファイル一式 + networkx。S3 は `aws s3 sync` のみ |
| 概念型 | problem / method / keyword。keyword は探索から既定で除外 |
| クエリ展開 | 英語クエリ生成を必須化。日本語要約・概念名も埋め込み |
| フィードバックログ | 入れない。根拠・経路・設定は出力 JSON に含めるのみ |
| Skill 配置 | 抽出・正規化の Skill は持たない（PR04 レビューで変更）。検索の入口は PR13 / PR14 で決める |
| 抽出コマンド名 | `rkgk extract` のまま（extract-graph 等は不採用） |
| 概念のグローバル ID | 正規化 Skill が代表名から slug を確定。以後不変 |
| 根拠とチャンクの対応 | 抽出は page + quote のみ。構築時に引用文を検索して chunk_id を付与 |
| モデル実装 | pydantic v2。JSON Schema をモデルから生成 |
| チャンク化 | 段落境界 + 上限 512 トークン、オーバーラップなし |
| Python 環境 | uv + Python 3.13、src layout、pytest、ruff |
| レイヤー構成 | DDD。domain / usecase / infrastructure と薄い CLI。domain は I/O を持たない（PR03 レビューで決定） |
| ページ対応 | 1ページ1ファイル `pages/001.md` |
| 図・数式 | `<!-- figure: N -->` / `<!-- equation: N -->` マーカー + 本文埋め込み。画像は受け取らない |
| paper.json | 最小項目 + 外部 ID 任意。S3 URI は含めない |
| キー配置 | 4桁ゼロ埋めディレクトリ。S3 とローカルで同一構造 |
| 採番台帳 | `papers/index.json` を前処理側が更新 |
